## 先把“慢”说清楚

机器变慢不是一个足够具体的问题。是所有接口都慢，还是只有某个路径？是持续发生，还是偶尔出现？开始操作前，记录异常发生的时间、影响范围和最近的变更，往往比多敲几条命令更有帮助。

同时保留最小现场：进程状态、资源概况、关键日志。重启可能恢复服务，也会让部分证据消失。是否重启，应由恢复优先级和现场信息共同决定。

## 用问题选择命令

每一条命令都应该回答一个问题，而不是为了“看一眼”。例如：

| 想确认的事 | 可以先观察的入口 |
| --- | --- |
| CPU 是否持续忙碌 | `top` 中的使用率与进程 |
| 是否存在运行队列或 I/O 等待 | `vmstat 1` 的连续采样 |
| 文件系统是否接近容量上限 | `df -h` |
| 连接集中在哪些状态 | `ss -s` |

单次快照很容易误导。负载高不等于 CPU 忙；空闲内存少也不一定意味着内存不足。要结合采样时间、系统缓存和业务指标，解释数字背后的含义。

## 一次只验证一个猜想

如果怀疑磁盘等待，就继续查看设备延迟和进程 I/O；如果怀疑线程阻塞，就把系统观察与应用线程信息对齐。每获得一条证据，都重新检查原来的猜想是否成立。

调整配置之后，记录改了什么、预期看到什么、实际发生什么。排查的价值不仅是让这一刻恢复正常，也在于留下下一次可以复用的推理过程。
