## 字段背后是约定

接口里一个看似简单的字段，往往包含许多没有写出来的决定。时间使用什么时区？空字符串与字段缺失是否相同？金额的单位是什么？这些问题越晚回答，客户端越容易形成不同的理解。

先为字段写出含义、单位和可选性，比提前设计一套庞大的扩展机制更实用。例如用整数表示最小货币单位时，也应明确币种与取值范围；返回时间时，应提供明确的偏移或统一的时区约定。

## 错误也是接口的一部分

客户端需要知道失败后该做什么。一个稳定的错误码可以用于程序判断，一条清楚的说明帮助人阅读，一个请求标识方便串联日志。

```json
{
  "code": "RESOURCE_NOT_FOUND",
  "message": "请求的资源不存在",
  "requestId": "example-request-id"
}
```

示例中的业务错误仍应搭配合适的 HTTP 状态码。不要让客户端依赖可随时改写的自然语言消息，也不要把内部堆栈直接暴露出去。

## 为变化保留适度空间

新增可选字段通常比改变现有字段含义更容易兼容，但也要确认消费者能够忽略未知字段。列表接口则需要明确排序规则；数据持续变化时，分页是否允许重复或遗漏，也应成为约定的一部分。

“留余地”不意味着预测所有未来需求。更可靠的做法是把当前承诺写清楚，让破坏性变更可以被识别，并给客户端合理的迁移过程。
